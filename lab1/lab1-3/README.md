# 实验一 · 任务 3：哲学家就餐与资源顺序分配

## 实验说明

> 「哲学家吃饭有很多条条框框，5人5个叉子，但是一人要用俩，叉子不够会打架。」

欢迎来到实验1-3，哲学家就餐。
在这里，我们的目标是：
5 位哲学家围坐一桌，每人左右各有一把叉子，一共 5 把。吃饭需要同时握着左右两把叉子。
现在的程序按「先左后右」的顺序取叉，会出现死锁——你要用资源顺序分配法改写，让所有哲学家都能吃完 5 轮。

1. 完成本实验前，你需要学习：基本C语言编程（建议至少学到指针和结构体部分），以及死锁产生的条件
2. 你需要先准备好做实验的环境，参见“实验包目录”，“环境要求”和“常见问题”这些部分来获得帮助。
3. 如果你不是很清楚，这里和代码里都会有详细的提示告诉你怎么做。

PS：你可以打开 VSCode 或者其它IDE，可以用分窗口的方式将这个文件和代码同时展示，这样使用效果更佳。

## 本部分实验教程

### 实验准备

请查看“实验包目录”，“环境要求”和“常见问题”

### 1-3的实验任务

你要做的是**一件事**：让两把叉子按编号从小到大的顺序申请。

提交文件是 `student/impl.c`，里面有三处 TODO：

| TODO | 位置 | 要写什么 |
|---|---|---|
| TODO 1 | `philosopher_run` 开头 | 比较 `first` 和 `second`，必要时交换 |
| TODO 2 | 交换之后 | 依次 `lab_fork_acquire` 两把叉子，再调 `lab_meal` |
| TODO 3 | 吃饭之后 | 依次 `lab_fork_release` 两把叉子 |

如果不做任何处理、每位哲学家都按「先左后右」取叉，
5 个人同时举左叉、各自等右边那把，就会形成循环等待——
这就是本实验要解决的死锁。`solution/9.c` 是改用资源顺序分配法之后的完整程序。

理解下述关键点：

1. 死锁的四个必要条件里，最容易破坏的是「循环等待」。资源顺序分配法就是给资源编号，规定只能按编号从小到大的顺序申请，循环等待就不可能形成。
2. 本实验里叉子编号就是 0..4，哲学家 `id` 需要叉子 `id` 和 `(id + 1) % 5`。前四位按编号从小到大取，本来就是「先左后右」；只有最后一位（哲学家 4）需要反过来，先取 0 号叉。
3. `lab_fork_acquire` 在叉子被占用时会阻塞，等待逻辑不用你写；你要做的只是决定**先申请哪一把**。
4. 释放的顺序不影响死锁，本实验只检查申请顺序。

**为什么 main 在测例里？**
（你可能会困惑：没有主函数怎么跑？）

`student/impl.c` 只包含一个函数，`main` 和叉子的实现都在 `tests/harness.c` 里。
这样「谁在什么时候拿了哪把叉子」由测例记录，
你不碰这些代码，测例才能判断你是不是真的按编号顺序申请的。

## 测例判什么

测例会创建 5 位哲学家，每人要吃 5 轮，共 25 顿饭。
不比对完整输出，只检查与实现方式无关的不变量：

| 检查项 | 说明 |
|---|---|
| `eaten` | 必须等于 25，即所有人都吃完了，没有被饿死、也没有死锁 |
| `order_violations` | 必须为 0，即每次都是先申请编号小的叉子 |
| `order_example` | 若违规，给出第一个例子，例如 `phil4_4_then_0` 表示哲学家 4 先拿了 4 号再拿 0 号 |
| `hold_violations` | 必须为 0，即每次吃饭时确实握着两把叉子 |
| `release_violations` | 必须为 0，即没有释放不属于自己的叉子 |
| 30 秒超时 | 死锁时直接判失败，并提示可能是死锁 |
| 连续 5 次运行 | 结果一致 |

### 为什么检查申请顺序，而不是等它死锁

死锁是概率性事件。按「先左后右」取叉的版本实测约一半的运行会卡死，
另一半能跑完——**只跑一次看不出问题**。

这正是原平台那类"平台会对操作进行检测"的判题方式最不可靠的地方。
本实验不赌死锁发生，而是直接检查申请顺序：
只要有一次先拿了编号大的叉子，就说明没有遵守资源顺序分配法。

### 为什么输出不能被伪造

`main` 在 `tests/harness.c` 里，你碰不到。每次运行测例都会生成一个随机前缀
（`nonce=xxxxxxxx`），所有有效输出行都带着它；测例只认带本次前缀的行。
取叉顺序、持叉情况、用餐次数全部由测例记录，所以「直接把结果 printf 出来」不会生效。

## 常见问题

**程序卡住不退出**

死锁。检查是不是还在「先左后右」地申请叉子——
哲学家 4 必须先拿 0 号叉，再拿 4 号叉，这样循环等待才被打破。

**`order_violations` 大于 0**

检查 TODO 1：比较 `first` 和 `second`，如果 `first > second` 就要交换。
`order_example` 会告诉你第一个违规的哲学家和两把叉子的编号。

**`hold_violations` 大于 0**

吃饭前没有把两把叉子都拿到。检查 `lab_meal(id)` 是不是在两次
`lab_fork_acquire` 之后调用。

**`release_violations` 大于 0**

释放了不属于自己的叉子。检查 `lab_fork_release` 的第一个参数是不是哲学家自己的 `id`。

**`eaten` 是 0 或小于 25**

如果没有调用 `lab_meal`，或者某一轮之后没有释放叉子，会导致后面的哲学家永远等不到叉子。

**不加交换的程序有时候能跑完，有时候卡死**

这是正常的，死锁本来就是概率性的。多运行几次观察，
真正可靠的方法是检查申请顺序，而不是"跑一次看看"。

**`Cannot create temporary file in C:\WINDOWS\`**

MSYS2 下 `make` 可能不把 `TMP`/`TEMP` 传给子进程，gcc 便退回到 `C:\WINDOWS` 建临时文件。
本目录的 Makefile 已把临时目录指向 `build/tmp`；若在别的项目里遇到，可手动设置：

```bash
export TMPDIR="$PWD/build/tmp" TMP="$TMPDIR" TEMP="$TMPDIR"
```

**测例输出的中文变成问号或方块**

Windows 控制台默认代码页通常不是 UTF-8。本目录的测例与检查脚本刻意只用 ASCII 输出，
避免这个问题。自己写测例时建议照做。

**`make` 报 `cc: command not found` 或临时文件错误**

MSYS2 的 `cc` 包装器在某些配置下异常。Makefile 已显式指定 `CC := gcc`。

## 与原始实验的区别

- 原平台的判题标准不公开；这里的每条断言都可读、可解释。
- 原题只要求"避免死锁"，本实验把「申请顺序」作为独立指标报告出来，
  即使某次运行侥幸没有死锁，顺序错误也逃不掉。
- 顺序违规会指出具体的哲学家和叉子编号，而不是只给一个"未通过"。
